## 1. What exists today (read-only survey)

- Capabilities are code strings checked by the application (for example `deposits.dispose`, `refunds.create`, `invoices.void`, `invoices.adjust`, `credits.apply`). The database checks the active actor and Property lists. There is no capability catalog table; access administration answers "unavailable". Adding `financial.approve` is therefore a code constant plus database function checks, not a catalog row.
- Refunds: `app.refunds` (Reservation Deposit, migration 21) and the Credit/Pet Refund services (migration 41, `refund.py`). Refunds run at once; there is no draft step and no Refund method column.
- Deposit dispositions run at once through `deposits.dispose` for three grounds only: `BR-DEP-022` (pet noncompliance), `BR-DEP-023` (voluntary early), `BR-LEASE-005` (unpaid Initial obligation). Termination bases are `VOLUNTARY_EARLY`, `CUSTOMER_VIOLATION`, `SIGNED_LEASE_OTHER` and `UNPAID_INITIAL_OBLIGATION`.
- Payment Allocation reversal exists (`payment_allocation.py`, `reverse_allocation`).
- Move-out inspection findings carry `pet_related` (migration 60). One-time charges and Damage charges exist (migration 65). The final Utility Invoice exists (migration 72). The Property due-days setting exists (9b).
- Units have no cleaning rate. Payment Methods are a global table `app.payment_methods`.
- Lease `end_date` is optional in the Lease draft and is checked only as later than the Start Date.
- Final Settlement has no code, no table and no traceability entry. docs/004 (DB-SETTLE-001 to 006) and docs/005 (API-070 to 072) already describe the design.
- Last migration: `20261010_75`. New migrations start at `20261011_76`.
- Traceability has 2445 entries, all `implemented`. 12 of the 13 new DL-069 rule IDs have no test (only BR-CREDIT-014 is mapped).

## 2. Order changes and why

- Refund methods and the joint-Signer recipient move from position 7 to position 3. Reason: slices 6 (Pet Deposit rest refunded) and 9 (Settlement Refunds) create Refunds, and every new Refund must carry a method and a reference note. Building the method list first avoids a later rework of those slices.
- Final Settlement (old 8) is split into two slices (draft and preview, then confirm and close). One slice would be too big for one checkpoint.
- HTTP and screens (old 10) are split into five slices, one per area, each with its own commit and security review.
- I recommend a security review also for slice 5 (hand-back VOID and credit Adjustment) and slice 10 (post-settlement corrections), because both change what a Customer owes. The takeover list does not require it; the owner decides (Q17).

- Change: new capability constant `financial.approve`. New generic tables `app.financial_drafts` (id, Property, kind, payload JSON with fixed schema per kind, prepared_by, prepared_at, reason, expected financial revision) and `app.financial_draft_events` (append-only: CONFIRMED, REJECTED, WITHDRAWN, with actor, time, reason). A draft has no financial effect. Confirm runs the kind's existing command function in the same transaction, with the confirming actor, and fails if the source changed since the draft (financial revision check). Each draft is confirmed at most once (unique partial index on CONFIRMED).
- Migration: `20261012_77` additive (two tables, guard triggers that forbid UPDATE and DELETE, SECURITY DEFINER functions `app.record_financial_draft`, `app.confirm_financial_draft`, `app.close_financial_draft`, EXECUTE to the runtime role only).

### Slice 10 design note (2026-10-06)

Written before any code, at the owner's request. Status: owner answers to Q-2026-10-06-36 received and built into this note (docs/010, 2026-10-06); follow-up points that do not block 10a are in Q-2026-10-06-37.

**Owner rules and how the design meets them (DL-068, DL-069, BR-SETTLE-012, BR-SETTLE-013 as amended, plan Q15 and Q17 answers):**

1. A Settlement is never reopened: no correction updates `app.final_settlements`, its closure snapshots (DB-SETTLE-002, 004, 006) or any record the confirm wrote; the 8a-1 closure guard stays as it is. Every correction is new rows: a header (DB-SETTLE-003) and typed effect links (DB-SETTLE-005), each pointing to exactly one ordinary financial record that the correction wrote in the same transaction.
2. A later fix is a new linked correction with a reason: the header carries the reason, the Settlement, the draft and a correlation id; every effect record names the correction in its audit context.
3. The same approvers as the Settlement: Staff prepare under `final_settlements.prepare` (plan Q3: the Settlement preparer capability also prepares corrections); only a `financial.approve` holder confirms (draft kind `SETTLEMENT_CORRECTION`, slice 2 functions for withdraw and reject; the same person may prepare and confirm only with `financial.approve`, plan Q4).
4. No time limit: no check on the age of the Settlement; only the chronology checks every writer has (not before the closure, not later than the clock plus 5 seconds).
5. Corrections pass the 8e-1 refusal (`app.refuse_closed_final_settlement_change`) and the 8e-2 refusal (`P5S01`) only through a linked correction row checked in the same transaction (deferred check), never through a session setting (8e-1 and 8e-2 security notes).

**Correction kinds** (owner answer 1 to Q-2026-10-06-36; each a variant of the draft kind `SETTLEMENT_CORRECTION`, prepared under `final_settlements.prepare` with a reason, confirmed only by `financial.approve`):

- `EXTRA_CHARGE`: a new one-time charge (an existing category, for example Miscellaneous or Damage, BR-INV-044) on a new issued Invoice with the Lease, to the Customer of the obligation it corrects, or to the Primary Tenant when it corrects nothing on an Invoice (owner answer 6: a Signer's own debt stays on that Signer's ledger, other Lease debt goes to the Primary Tenant, BR-SETTLE-016); Due Date = issue date + Property due-days, with the existing override; no Late-payment Charge on a correction Invoice (the 8e-1 refusal of Late-payment Decisions after closure stays). Debt stays on that Customer's ledger.
- `CHARGE_REDUCTION` (the fifth kind, owner answer 1: a clear fix for a wrong charge that is still unpaid): a linked credit Adjustment that removes the wrong unpaid amount; refused when it would release paid value (that is a `REFUND`).
- `REFUND` (a wrong charge that was paid, or a returned Settlement Refund): a linked credit Adjustment on the Settlement obligation; the part paid by a Payment allocation or a Credit application is released as today (migration 67) and the part paid by a Deposit application is released through a new Deposit application reversal (owner answer 2), so the Deposit holds it again; a linked Refund pays the released value to its owner (Credit Refund to the Credit's Customer, Deposit Refund to the Primary Tenant or the agreed Signer, BR-REFUND-015). A `REFUND` always pays a Refund; an unpaid part in the same Adjustment is removed with it. A returned Settlement Refund (8d note) records the verified return and a new Refund in one correction.
- `RETURNED_PAYMENT` (owner item and owner answer 5): for a Payment whose Credit or Deposit the Settlement used, the correction reverses, in one transaction, the Settlement's Credit applications sourced from that Payment's Credits, the Deposit applications of a Deposit that Payment funded, the Payment's other allocations and Credit applications, then the Credit reversals, the Deposit receipt reversal and the Payment reversal; the debt comes back on the original obligations and stays on their Customers' ledgers (BR-SETTLE-016). A Settlement Refund already paid from a Deposit that the returned Payment funded cannot be undone (money left the Property): it becomes an `EXTRA_CHARGE` to the Deposit owner in the same correction. The same returned-Payment draft also works for a Payment with no closed Settlement (owner answer 5): it passes the slice 7 and 8g refusals only through its own linked record, so it ends both lasting blocks; tested with a returned third-party Payment whose adjustment Credit was released to another Customer. Its record shape and preparer capability are Q-2026-10-06-37 points 2 and 3.
- `ADJUSTMENT_REVERSAL` (owner request in 8g, owner answer 7): the mistaken credit Adjustment reversal of the slice 10 entry above; before closure an ordinary draft prepared under `invoices.adjust`, after closure only inside a correction prepared under `final_settlements.prepare`; `financial.approve` confirms both.
