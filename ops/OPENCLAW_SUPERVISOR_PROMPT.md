# Property Rental deterministic supervisor contract

This document is an operator-readable contract. The dispatcher must never inject it into an implementation or review session.

The OpenClaw schedule runs `scripts/openclaw-supervisor-dispatch.sh`. That entry point performs only compact-state reconciliation, deterministic roadmap selection, stage routing, lock and process monitoring, failure classification, durable evidence management, publication-state reconciliation, and health/progress signaling. It must not perform model-heavy product work.

`scripts/openclaw_dispatch.py` is the single mandatory model-invocation route. Before any implementation, repair, or review model starts, it creates a one-use repository-owned manifest containing the exact candidate, stage, repository, branch, HEAD, repository/worktree fingerprint, preserved-worktree fingerprint, task hash, unique usage and budget paths, token policy, live candidate-stage record hash, dispatcher process identity, and stage-specific writable paths. A per-invocation authorization secret is passed only to the child environment; the wrapper proves its live dispatcher parent, and direct, reused, drifted, incomplete, or candidate-record-mismatched manifests fail before model execution. The conversational supervisor must never call `hermes-property-rental` directly.

Every candidate has these separately persisted stages: reconciliation and dispatch, implementation, deterministic verification, independent review, publication, post-publication reconciliation, and next-candidate activation. Activation and implementation are distinct scheduled transactions: a successful activation cycle stops after its exact metadata commit, push, CI, and SHA reconciliation, and implementation can begin only in a later scheduled cycle. Activation persists its base, candidate, timestamp, exact changed-path set, and tree. A restart may complete only target files whose worktree and index contents are individually proven to be either the base or the deterministic target; already-complete roadmap metadata may therefore yield a two-path activation without being misclassified as missing work. Each model stage is a unique fresh one-shot session receiving only the deterministic compact packet built from current state, exact fingerprints, the exact bounded authorities, include/exclude boundaries, substage acceptance, authorization, current recovery state, direct product/test paths, and output contract. Repository-local continuity instructions and exact requirement excerpts are materialized in the packet; isolated Hermes must not look up an external skill, reread compact-state or canonical files, use todo/planning tools, or rediscover broad repository context. V1-019 implementation is deterministically divided, within its one approved scope, into fresh sign-in, MFA/recovery, session, and account/capability substages. Full supervisor prompts, prior transcripts or reasoning, unrelated diffs, Makefile, raw logs, and stale errors are forbidden inputs.

Implementation uses the repository-owned Hermes wrapper with provider `openai-codex`, model `gpt-5.6-sol`, and requested reasoning `high`. Authorized defect recovery uses a distinct fresh guarded Hermes session with the same model, `high` reasoning, and ordinary ceiling, followed by a separate fresh independent review. Independent review uses a distinct fresh guarded Hermes `gpt-5.6-sol` session with requested reasoning `xhigh` and read-only tools. The ordinary implementation or ordinary-repair session ceiling is exactly 60,000 cumulative counted tokens. An independent review is preclassified at 90,000; 120,000 is permitted only when the exceptional complex-review reason, fingerprint, and scope were recorded before invocation. Implementation cannot promote its ceiling. Unsupported invocation configuration and pre-model capability failures are automatically recoverable routing faults: they release the reservation, consume no candidate attempt, and require no Owner authorization.

The repository-local Hermes plugin enforces cumulative usage before each provider API call. Counted usage is exactly `input_tokens + output_tokens`. Cache-read tokens are persisted and reported separately without double-counting. Before a new request starts, the guard uses the validated serialized-request estimator, persists its serialized byte classes, divisor, prior provider-observed floor, carried shortfall, fixed 1,024-token validation margin, and at least 2,048 completion/checkpoint tokens beneath the unchanged stage ceiling. One byte is never treated as one token. Unavailable reliable estimation is a recoverable zero-model-attempt routing configuration and never claims the configured ceiling was reached. Individual and cumulative bounded tool outputs are capped before they can inflate another request. A request that cannot fit is stopped before provider execution; ordinary in-flight overshoot is a reservation violation, not normal operation. Provider authentication is withheld from each isolated session until the guard registers inside that actual chat process; a preflight-process attestation cannot stand in for chat-process attachment.

Hermes implementation and ordinary-repair sessions have repository-scoped reads, dispatcher-allowlisted candidate product writes, read-only `git status` and `git diff`, and a restricted terminal that accepts only one repository-owned allowlisted `make` verification target from the repository root. Patch enforcement parses every file-operation endpoint, including both move endpoints, and rejects unknown or partially parsed headers. Initial implementation cannot write automation, build-entry, scheduler, or canonical-policy paths; ordinary repair can write only the exact persisted candidate paths; independent review cannot write. Database verification is permitted only as `make database-test` from the repository root. Canonical documents may be read when routed but not changed. Git commit/push, GitHub mutation, direct database commands or credentials, cron control, background process control, unrestricted browser access, and delegation are forbidden. Final verification, independent review, publication, and scheduler control remain separate stages.

The shell preflight executes the same authoritative Python lifecycle and blocker classifier used by the dispatcher. A capability-only preserved continuation is accepted only for the exact candidate, authorized branch, synchronized HEAD, dispatcher-recorded preserved-worktree fingerprint and path hashes, approved scope, `owner_action: none`, no failed or known-failing check, and no overlapping worker. Its structured failure must be `verification_tooling_unavailable`; a free-form `partial` label is never sufficient. It routes directly to deterministic verification without rerunning implementation. Genuine Owner-policy, scope ambiguity, suspected-secret, protected-operation, conflicting-work, and bounded-attempt exhaustion categories remain blocked. A real in-scope failed test enters the bounded ordinary repair path.

Failures are classified before counters change. Pre-model infrastructure failures release reservations and consume no implementation, verification, review, or repair attempt. Gateway/network, unsupported configuration, invalid delivery, ceiling, repeated call, deterministic test, fixture, review, publication, remote CI, state reconciliation, overlap, Owner-policy, protected-operation, and repository-integrity failures remain distinct durable records. An implementation token-ceiling stop without a protected boundary schedules a fresh bounded same-substage session under a changed routing fingerprint and does not request Owner action. Owner action is permitted only when that bounded recovery budget exhausts or a protected decision appears. Ordinary authorized defects have at most two recovery attempts per exact substage/fingerprint. Protected decisions never inherit that authority.

Repeated calls are keyed by normalized identity and arguments plus exact repository, compact-state, process-state, substage/recovery generation, and prior-result category. An unchanged failed call is suppressed before a second non-progressing retry, while its safe underlying exit/category evidence and exact next eligible action remain visible. Completed, blocked, exhausted, continuation-used, and published markers are written atomically for the exact fingerprint. A scheduled ceiling recovery is recorded as pending rather than terminal; its changed routing fingerprint remains eligible and health reporting may call recovery pending only while that retry is actually dispatchable.

The supervisor lock records PID plus verified process identity. A lock is stale only when that identity is absent or mismatched; age alone cannot recover it. Dispatch also refuses relevant Hermes, repository-bound interactive or execution-mode Codex worker, test, database-test, dispatcher, or supervisor overlap before successor metadata or product files can change. An overlap is an automatically recoverable routing condition: it consumes no product or repair attempt and requests no Owner authorization. No terminal status depending on a marker may be returned before that marker is durable.

Every model usage record contains returned model, returned reasoning when exposed, invocation route, session ID, API calls started/completed, input/cache-read/output/reasoning tokens, counted total, applicable cumulative boundary, boundary and next-call-blocked flags, any in-flight overshoot, stage, result, repository fingerprint, and exact next action. A provider-omitted field is recorded exactly as `unavailable from provider`; it is never inferred. Gateway, fallback, implementation, later cycle, review, verification, ceiling, publication, and reconciliation events are never concatenated.

Publication requires foreground-observed deterministic gates, a fresh independent `passed: true` verdict, an exact reviewed path allowlist, clean scope/secret/canonical/diff checks, no overlapping process, a normal push, successful GitHub Actions, and local/upstream/remote equality. Compact state is then reconciled before model-free selection of the next exact durable-roadmap successor. The approved V1-019 recovery is a terminal scope boundary for this workflow: V1-020 remains unselected after V1-019 publication.

Health reporting distinguishes intentionally disabled, unhealthy, healthy idle, Owner-policy blocked, protected-operation blocked, implementation, verification, review, publication, reconciliation, recovered, completed, and repair-exhausted states. Post-exit restoration binds its attempts to durable supervisor run sequences created after its captured sequence floor; inherited `consecutiveErrors` never becomes a new bounded attempt. A recoverable failed run with a preserved worktree, no protected boundary, `recovery_pending: true`, and remaining budget leaves the supervisor enabled through the exact bounded retry and emits `RECOVERY_SCHEDULED`. `RESTORATION_FAILED_CLOSED` is terminal and is reserved for unknown/protected failures or genuine bounded exhaustion. Notifications are deduplicated by notification type plus material state fingerprint and always state the affected subsystem, scheduler enabled state, project stage, cause, recovery state, exact next action, and whether Owner action is genuinely required.

Never broaden roadmap scope, invent canonical/product/security policy, handle secrets or production access, perform destructive operations, force-push, rewrite history, or publish with a failed or unobserved gate.
